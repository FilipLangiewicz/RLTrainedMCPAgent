### The cause

This run replaces the first run, `baseline-qwen3-5-4b`. In the first run, a GPU memory error left the first process without free memory, so 85 tasks failed with no call. The code now frees the memory after a failed task. The 115 tasks that ran in the first run have the same calls and grades in this run.

1. The main problem is the project. The model repeats `project = DT` or `project = PROJ` until the loop rule, for example `test-018`, `test-059`, `test-102`. In `test-140`, it finds `DATA` with a search and completes the task.
2. The model takes a topic or a name as a project: `SPORTLAND` (`test-115`), `SECURITY` (`test-185`), `FACT_SALES` (`test-155`), `ZWROT` (`test-159`).
3. The model writes more than one call in one output in 65 of 200 tasks. Long outputs cause the 4 GPU memory errors: `test-031` (395 calls), `test-065` (263 calls), `test-148` (160 calls) and `test-159` (268 calls). The next tasks run normally.
4. The model searches for a short form of a first name (`Zosia`, `Bartek`, `Wojtek`, `Mark`), and the search finds no person.
5. The model guesses ids in place of a read: the board 10000 (`test-063`, `test-193`) and the transition 3 (`test-035`, `test-129`).
6. The model often uses the tools correctly when the instruction has the key. Thus its `easy` score is 0.472, and it has the highest `multi_step` score of the six baselines.

### What SFT and RL must teach

1. Write one call, then stop and read the result.
2. Use the correct JQL form: `summary ~ "word"`, `labels = x`, `sprint in openSprints()`.
3. Find the project and the key with a tool. Do not copy examples from the tool descriptions.
4. Do not repeat a call that failed. Read the error and change the call.
5. Use `jira_create_issue` to create an issue, not a search for the new title.
6. Start each refusal with `ODMOWA:`, and only in the correct cases.
7. Report only what the tools confirm.
